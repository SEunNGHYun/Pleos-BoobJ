## 실행과 재현

- `npm run build`, `npm test`, `npm run test:smoke` 재실행 성공. 전체 회귀 실행 당시 API·계산 25건과 DB 8건. 중복 완료를 추가한 후 `npm run test:db` 9건 통과. [빌드](build.log) · [회귀](test.log) · [장애](smoke.log) · [완료 재실행](database-completion.log) · [거절](rejection.log)
- [두 화면 준비 절차](../../../api/two-screen-demo.md)에 따라 로컬 DB와 서버를 시작하고, 등록된 식당과 역할별 개발 토큰을 사용한다. 차량에서 메뉴·수량·픽업 장소 선택 → 주문 실행 → 식당에서 같은 ID 조회 → 조리시간 및 MOCK ETA 입력 후 수락 → 차량 상태 새로고침.
- 거절 시연은 별도 PENDING 주문에서 사유를 입력하고 거절한 뒤 고객 주문 상세를 확인한다. 기존 수락 주문을 거절하면 서버 상태 충돌로 처리된다.
- SDK 구분. Pleos Connect 에뮬레이터에서 AndroidX 차량 UI와 실제 로컬 HTTP를 실행했다. 내비 경로·ETA·접근·도착 SDK 콜백은 연결 및 검증하지 않았다. ETA는 식당 수동 MOCK 입력이다. 조리 시작·준비·완료는 테스트가 DB 함수를 직접 호출한 수동 이벤트다.

## 11월 8일 장애 목록

1. 실제 공간 예약의 저장과 입장 통제가 가장 큰 단절이다. 위치별 예약 구간·실제 점유·반환을 모델링하고, 식당 수락 트랜잭션에서 기존 조리 예약과 함께 확정한다. 1대·3분 가정과 초과 점유 정책을 검토하고 독립 DB 세션의 동시 요청을 검증한다.
2. 기존 조리 시작·READY·완료 함수를 권한·버전·요청 키가 있는 API로 연결한다. 실제 입장과 인도 확인을 연결하고 중복 완료 시 상태와 공간 해제를 검증한다.
3. ETA 갱신·지연 이벤트를 연결한다. LOCK 전 대안 제시·기존 예약 보존과 LOCK 후 조리시각 보존을 화면까지 검증한다.
4. 위 흐름을 MOCK으로 먼저 완주한다. 실연동은 설치 버전에서 좌표 경로·ETA·도착 콜백이 동작하는지 별도 검증한 뒤 시연 범위를 확장한다.

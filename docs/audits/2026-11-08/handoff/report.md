# 11월 8일 차량 인도형 픽업 시연

기존 차량 화면·식당 웹과 서버 계약, SDK 조사 기록을 대조했다. 식당의 수동 조리 시작·준비 완료·입장 확인·인도 완료·취소를 기존 DB 함수에 연결했다. 각 작업은 식당 권한과 주문 버전을 검사하고 요청 키·응답을 같은 트랜잭션에 저장한다. 차량은 기존 조회에서 인도 완료를 표시한다.

| 구분 | 결과 |
|---|---|
| 주문 생성 → 접수 및 예약 → 조리 예정 | 성공. 로컬 HTTP에서 PENDING → ACCEPTED / RESERVED, 조리 시작 예정 조회 |
| 수동 조리 → 준비 완료 → 입장 → 인도 | 성공. 실제 테스트 시간으로 예약 구간에 진입해 COOKING → READY, ARRIVED / OCCUPIED, COMPLETED / RELEASED 확인. 고객 상세와 식당 목록의 같은 주문 응답 비교 |
| 취소·잘못된 순서·권한 | 성공. 조리 전 취소 성공, 조리 시작 후 취소·조기 입장·준비 전 완료는 409, 고객의 식당 수동 작업은 404 |
| 중복 완료 | 성공. 같은 키 재전송은 동일 응답, 새 키와 최신 버전으로 완료를 반복해도 버전 5 유지 |
| 네트워크 장애 | 성공 범위는 웹 health 프록시의 API 중단 응답 및 같은 완료 요청 재시도. 응답 유실을 주입한 브라우저·차량 E2E는 미검증 |
| Pleos 내비 SDK | 미검증. 앱 내 SDK 호출부 없음. MOCK ETA는 식당 입력, 도착·인도는 식당의 수동 확인이며 SDK 콜백을 사용하지 않음 |
| 신규 전체 화면 시연 | 미검증. 새 UI 빌드는 통과했고 전체 전이는 로컬 HTTP 시나리오로 실행. 양쪽 화면에서 완료까지 다시 조작하거나 캡처하지 않음 |

[인도 시나리오 로그](scenario.log) · [API·DB 회귀](test.log) · [웹 장애 테스트](smoke.log) · [웹 빌드](build.log) · [Android 빌드](android.log)

시연 재현은 [두 화면 시연 안내](../../../api/two-screen-demo.md)의 수동 인도 단계를 따른다. 자동 시나리오는 안내의 RUN_PICKUP_DEMO 명령으로 실행한다. 일반 npm test에서 이 시나리오는 시간 대기를 줄이기 위해 제외된다.

## 다음 장애 및 우선순위

1. 실제 두 화면의 인도까지 새로 시연하고, 연결 끊김·복구 후 요청 재전송을 화면에서 재검증한다.
2. 독립 PostgreSQL 세션에서 공간 경쟁을 검증한다. ETA 지연·만료 예약의 재계획 및 기존 접수 건에 대한 공간 배정 정책을 확정한다.
3. 검증된 설치 버전에서 Pleos 내비 SDK 경로·ETA·도착 콜백을 확인하고 수동 입장과 구분한다.

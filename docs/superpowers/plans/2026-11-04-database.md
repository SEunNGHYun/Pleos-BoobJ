# Pickup Database Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans to implement inline.

**Goal:** Create a tested Supabase-compatible schema for users, restaurants, pickup locations, orders and capacity-limited cooking reservations.
**Architecture:** PostgreSQL migrations, server-only data access, RLS, atomic reservation procedures. Existing Android modules remain untouched.
**Tech Stack:** Supabase PostgreSQL, PL/pgSQL, Node test runner with disposable PGlite PostgreSQL instances.
**Spec:** docs/architecture/supabase-data-model.md

## Global Constraints
- One order consumes one cooking place, per restaurant rather than per pickup location.
- Preserve agreed three state groups; COOKING is LOCK.
- No cloud connection is currently configured. Do not claim hosted deployment.
- Do not change Android source or include database secrets.

## Review Focus
- Overlapping reservations at exact interval boundaries.
- Capacity reduction and simultaneous requests.
- Cross-restaurant pickup/reservation references.
- Forbidden state changes and actual cooking overruns.
- Browser role access and unauthenticated RPC calls.

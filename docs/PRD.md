# 밥맞J 제품 요구사항 정의서

| 항목 | 내용 |
|---|---|
| 문서 상태 | MVP 검토 초안 |
| 작성일 | 2026년 11월 8일 |
| 제품 범위 | Pleos 차량 앱, 식당 운영 웹, 주문·조리·픽업 상태 관리 |
| 구현 현황 근거 | 2026년 11월 7일 통합 점검 및 후속 두 화면 시연 기록 |

## 1. 문제와 목표

차량 운전자는 주문한 음식이 언제 준비되고 어디서 받을 수 있는지 알아야 한다. 식당 직원은 차량의 도착 시점에 맞춰 조리를 시작하고, 차량이 들어올 자리를 확보한 뒤 음식을 전달해야 한다. 차량이 늦어지거나 픽업 공간이 이미 사용 중이면 조리 일정과 현장 안내가 달라진다.

밥맞J는 차량에서 주문한 음식을 식당이 지정한 장소에서 하차 없이 받을 수 있게 한다. 같은 주문에 차량 도착 예정 시각(ETA), 식당 조리 일정, 픽업 공간 상태를 연결해 운전자와 직원이 다음에 할 일을 확인할 수 있게 한다.

## 2. 대상 사용자와 범위

| 사용자 | 필요한 정보와 행동 |
|---|---|
| 운전자 | 메뉴·수량·픽업 위치를 선택해 주문하고, 접수 여부와 확정 픽업 시간, 진입·대기 안내를 확인한다. |
| 식당 관리자 | 판매 메뉴와 기본 조리시간, 픽업 위치와 운영 조건을 관리한다. |
| 식당 직원 | 주문을 수락하거나 거절하고, 조리 시작·준비 완료·차량 입장·음식 인도를 기록한다. |

MVP는 한 주문을 한 식당에서 수락해 지정 장소에서 인도하는 흐름을 다룬다. 결제와 배달은 후속 범위다. 픽업은 식당이 지정한 안전한 진입·대기·인도 장소에서 진행하며 불법 갓길 정차를 안내하지 않는다.

## 3. 기본 사용자 흐름

1. 운전자가 차량 앱에서 메뉴와 수량을 고르고, 지정 픽업 위치와 진입 안내를 확인한 뒤 차량번호와 연락처를 포함해 주문한다.
2. 식당 직원이 대기 주문을 확인하고 예상 조리시간을 입력해 수락한다. 서버가 조리 일정과 픽업 공간을 함께 확보하면 양쪽에 확정 시간을 표시한다. 거절하면 운전자에게 사유를 표시한다.
3. 차량 ETA가 바뀌면 조리 시작 전까지 계획을 다시 검토한다. 식당에는 조리 시작 예정 시각을 안내하고, 직원이 시작을 확인하면 조리 계획을 고정한다.
4. 도착 약 3분 전에 직원에게 픽업 준비를 알린다. 차량 도착과 실제 입장은 각각 기록하며, 공간이 사용 중이면 운전자에게 지정 대기 위치를 안내한다.
5. 직원이 음식 준비와 차량 입장을 확인한 뒤 차량에 음식을 전달한다. 인도 확인과 함께 주문을 완료하고 픽업 공간을 반환한다.

## 4. 기능 요구사항과 수용 기준

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| FR-01 | 메뉴·픽업 위치 관리 | 식당은 판매 메뉴, 가격, 메뉴별 기본 조리시간과 복수 픽업 위치의 주소·좌표·진입 안내를 관리한다. 주문 당시 메뉴와 선택 위치 정보는 이후 변경에도 보존된다. |
| FR-02 | 차량 주문과 상태 조회 | 운전자는 판매 중인 메뉴와 같은 식당의 유효한 위치로 주문한다. ETA가 없어도 접수 대기 상태로 저장한다. 같은 요청을 재전송해도 주문은 한 건만 생성된다. |
| FR-03 | 식당 접수와 시간 확정 | 소속 식당 직원만 수락·거절한다. 유효한 ETA, 식당 입력 조리시간, 주방 및 공간 수용량을 확인한 뒤 수락·조리 예약·공간 예약을 한 번에 확정한다. 공간 충돌 시 주문은 대기 상태를 유지하고 가능한 대안을 안내한다. 거절 사유는 차량에서도 확인할 수 있다. |
| FR-04 | ETA 변경과 조리 일정 | ETA는 선택한 픽업 위치를 기준으로 하고 측정 시각과 출처를 기록한다. 오래되거나 순서가 뒤바뀐 관측값이 최신 ETA를 덮어쓰지 않는다. 조리 시작 전에는 재계산 가능 여부를 검토하고, 실패하면 기존 예약을 보존한다. 확정 픽업 시간 변경은 사용자 동의를 거친다. |
| FR-05 | 조리 안내·시작·준비 완료 | 메뉴의 기본 조리시간은 주문 전 안내에, 직원이 입력한 조리시간은 실제 일정에 사용한다. 조리 시작 예정 알림을 제공하고, 시작 확인 이후에는 ETA가 바뀌어도 확정된 조리 시작 시각을 유지한다. 준비 완료 시 주방 용량을 반환한다. |
| FR-06 | 접근 안내와 공간 점유 | 도착 약 3분 전 준비 알림을 제공한다. 도착 신호는 차량 상태에 반영하고, 직원이 입장을 확인한 시점부터 공간을 실제 점유로 기록한다. 예약 구간이 지났더라도 실제 점유 중이면 다음 차량 입장을 제한한다. |
| FR-07 | 음식 인도와 공간 반환 | 음식 준비 완료와 차량 입장이 모두 확인된 주문만 인도 완료할 수 있다. 주문 완료와 공간 반환은 함께 기록하고, 동일 요청을 재시도해도 완료 시각과 반환 기록이 한 번만 반영된다. |
| FR-08 | 장애와 동시 요청 처리 | 연결 실패를 화면에 표시하고 재조회할 수 있다. 같은 공간을 동시에 확보하려는 요청은 설정된 수용량을 넘지 않는다. 상태 갱신 충돌은 최신 상태를 재조회해 처리하며, 실패한 변경의 중간 상태는 저장하지 않는다. |

### 상태와 시간 표시

- **주문**은 접수 대기, 수락, 거절, 완료를 구분한다.
- **조리**는 미예약, 예약, 조리 중, 준비 완료를 구분한다. 조리 시작 시 일정이 고정된다.
- **공간**은 미예약, 예약, 사용 중, 반환을 구분한다. 위치를 선택했거나 시간이 제안된 경우에는 확정 예약으로 표시하지 않는다.
- **차량**의 ETA와 도착 상태는 실제 입장 및 공간 사용 상태와 별도로 관리한다. 시연에서는 수동 입력 ETA를 MOCK으로 표시한다.

### 권한과 데이터

주문 고객과 해당 식당의 권한 있는 직원만 주문 상세를 확인할 수 있어야 한다. 차량번호와 연락처는 픽업 운영에 필요한 화면과 사용자에게만 제공한다. 운영 인증, 개인정보 보관 기간과 삭제 기준은 실제 운영 전 확정한다.

## 5. 현재 구현과 MVP 완료 조건

| 영역 | 11월 7일 기록 기준 |
|---|---|
| 주문·접수 | Pleos 에뮬레이터에서 생성한 주문이 식당 웹에 같은 ID로 표시되고, 식당 수락 후 차량에서 접수 상태와 MOCK 기반 예상 픽업 시간을 확인했다. 식당 거절과 고객 API의 사유 조회도 확인했다. |
| 조리 | MOCK ETA와 식당 입력 조리시간으로 시작 일정을 계산한다. 시작·준비 완료·완료는 DB 함수 테스트에서 확인했으며, 직원 화면에서 호출하는 흐름은 남아 있다. |
| 픽업 공간 | 위치 선택·저장은 확인했다. 실제 공간 예약·점유·반환과 독립 요청 간 중복 예약 방지는 구현이 남아 있다. |
| ETA·운영 환경 | 지연·충돌·조리 시작 후 일정 고정은 일부 계산과 DB 테스트에서 확인했다. Pleos 내비 ETA·도착 이벤트 연결과 호스팅 DB·운영 인증 검증은 남아 있다. |

**시연 완료 조건**은 로컬 환경에서 MOCK ETA를 사용해 주문 생성부터 식당 접수, 공간 확정, 조리 시작·준비 완료, 차량 입장, 인도·공간 반환까지 두 화면에서 이어서 확인하는 것이다. 거절, ETA 지연, 공간 충돌, 완료 요청 재전송도 별도로 재현한다.

**파일럿 운영 조건**은 Pleos 환경에서 실제 ETA·도착 신호를 검증하고, 운영 인증과 DB에서 권한·동시 예약 제한을 확인하는 것이다. 참여 식당의 진입·대기·인도 장소와 초과 체류 대응 절차도 확정한다.

## 6. 성과 지표와 결정 사항

파일럿 지표는 아래와 같이 제안한다. 목표값은 첫 운영 데이터를 바탕으로 정한다.

| 지표 | 측정 방법 |
|---|---|
| 접수 응답 시간 | 주문 생성부터 식당 수락 또는 거절까지 걸린 시간 |
| 확정 시간 내 준비율 | 픽업 구간 종료까지 준비 완료된 주문 ÷ 픽업 시간이 확정된 주문 |
| 픽업 대기 시간 | 차량 도착 확인부터 음식 인도까지 걸린 시간 |
| 픽업 완료율 | 인도 완료 주문 ÷ 수락 주문. 동일 기간의 수락 주문을 기준으로 추적 |
| 공간 운영 오류 | 수용량을 초과한 예약·실제 점유 건수와 인도 후 미반환 건수 |

시연 전에는 장소별 수용량과 예약 구간 길이, 지각·미도착·초과 체류 처리, 대체 시각 동의 방식을 확정해야 한다. 파일럿 전에는 ETA 누락·오래된 관측값 처리, 주문 전 조리시간 안내 여유, 알림 방식, 운영 인증과 개인정보 정책을 확정해야 한다. 기존 작업 기록에 있던 11월 8일 핵심 시연과 11월 14일 조기 제출은 당시 목표 일정이다.
